# КВАРД — регламент пользовательского дизайна

Статус: утверждён пользователем 2026-11-25  
Область действия: пользовательская часть продукта КВАРД  
Основная ветка: `main`

Этот документ фиксирует рабочие ограничения и последовательность разработки пользовательского интерфейса. Он дополняет существующие документы дизайн-системы и глобального плана, не заменяя их без отдельного решения.

## 1. Обязательные решения пользователя

- Разрабатываем то, что видит конечный пользователь.
- Административную панель временно исключаем из текущего объёма работ.
- Не изменять административные компоненты, стили, маршруты, серверные API, авторизацию, роли и права доступа в рамках пользовательского редизайна.
- Разработка ведётся непосредственно в основной ветке `main`.
- Не создавать отдельные ветки для дизайна, функций, экспериментов или исправлений.
- Не удалять и не чистить существующие ветки без отдельного запроса пользователя.
- Сохранять бизнес-логику, архитектуру, интеграции и реально работающие функции.
- Не подменять реальные функции декоративными элементами, фиктивными метриками или ложными статусами.
- Не считать задачу завершённой без проверки результата.

## 2. Утверждённое визуальное направление

- Основное направление: Balanced.
- Общий характер: современный, профессиональный, сдержанный SaaS для разработки и управления AI-инструментами.
- Публичная поверхность: Vercel — ориентир по ясности, типографике, композиции и сдержанности.
- Рабочая среда: Lovable — ориентир по взаимодействию с Builder, диалогу, предпросмотру и редактированию.
- Единая визуальная система должна объединять все пользовательские экраны.
- Конкретные значения цветов, шрифтов, размеров и токенов считаются окончательными только после сверки действующих файлов и отдельной фиксации в журнале решений.

## 3. Область текущей работы

Включено:
- вход, регистрация и приветствие;
- пользовательская оболочка приложения, навигация и глобальные действия;
- главная рабочая среда и проекты;
- Project Studio / Builder, чат, preview, файлы и код;
- пользовательские AI-агенты и профили запуска;
- Business Agents / Workforce;
- интеграции;
- диагностика и пользовательский журнал событий;
- журнал / новости;
- пользовательские настройки;
- общие компоненты, состояния, доступность, адаптивность и motion design;
- публичный сайт продукта, если он входит в подтверждённый пользовательский scope.

Исключено до отдельного решения:
- Admin Control Center и все его страницы;
- административные API и серверные проверки;
- административные роли, разрешения, MFA и настройки доступа;
- администраторские метрики, аудит и управление платформой.

Если пользовательский экран зависит от административного API, не менять этот API в рамках задачи. Зафиксировать зависимость и предложить безопасное решение отдельно.

## 4. Правила Git и внесения изменений

1. Перед работой проверить актуальный HEAD ветки `main`.
2. Все изменения выполнять непосредственно в `main`.
3. Не вызывать операции создания ветки.
4. Не переключать базовую ветку и не переносить работу через pull request.
5. Перед записью файла получить его актуальное содержимое и SHA.
6. Не перезаписывать изменения, появившиеся после последней проверки.
7. Делать небольшие логические коммиты с понятными сообщениями.
8. После каждого логического этапа запускать доступные typecheck, lint, tests и build.
9. Проверять diff коммита: административные файлы не должны попадать в пользовательский редизайн.
10. При конфликте, неожиданном изменении main или неясном состоянии остановиться и сообщить пользователю, а не создавать обходную ветку.

Существующие ветки не удалять. Запрет относится к созданию новых рабочих веток и не является разрешением на чистку старых.

## 5. Последовательность работ

### Этап 0. Пользовательский аудит
- Сверить пользовательские маршруты с реальными компонентами.
- Инвентаризировать экраны, состояния, зависимости и API.
- Зафиксировать исходное состояние сборки и тестов.
- Проверить desktop, tablet, mobile, light и dark.
- Получить реальные скриншоты интерфейса, если доступна браузерная среда.
- Не изменять административную панель.

### Этап 1. Исследование конкурентов
- Изучить реальные пользовательские интерфейсы Vercel, Lovable, Replit, Cursor, Linear, Stripe и релевантных продуктов.
- Сравнить навигацию, Builder, рабочие панели, типографику, плотность данных, состояния и адаптивность.
- Сохранять ссылки, скриншоты, дату проверки и конкретный вывод по каждому референсу.
- Не копировать чужой бренд или интерфейс целиком.

### Этап 2. UX-архитектура
- Зафиксировать карту пользовательских маршрутов.
- Описать ключевые сценарии.
- Уточнить информационную архитектуру и переходы.
- Сохранить соответствие реальным возможностям backend.

### Этап 3. Дизайн-фундамент
- Согласовать брендовые элементы, токены, типографику, сетку, spacing, радиусы, elevation и motion.
- Определить единые правила light/dark.
- Согласовать состояния компонентов и их доступность.

### Этап 4. UI Kit
- Создать каталог общих компонентов.
- Для каждого компонента определить варианты, состояния, поведение и адаптивность.
- Устранить дубли и конфликтующие стили только после оценки влияния на действующие экраны.

### Этап 5. Пользовательская оболочка
- Навигация, заголовки страниц, глобальный поиск, уведомления и системные действия.
- Проверить клавиатурное управление и мобильную навигацию.

### Этап 6. Рабочая среда и Builder
- Главная, проекты, создание проекта.
- Studio, chat/composer, agent progress, preview, files, code.
- Ошибки, подтверждения, отмена, повторный запуск и публикация.

### Этап 7. Пользовательские AI Agents и Business Agents
- Каталоги, карточки, формы настройки, инструменты, политики подтверждений и статусы.
- Статусы и метрики отображать только по реальным данным.

### Этап 8. Остальные пользовательские разделы
- Интеграции, диагностика, журнал, настройки, вход и регистрация.
- Сохранить реальные интеграции и поведение API.

### Этап 9. Motion и адаптивность
- Согласованные переходы и микроанимации.
- Desktop, tablet и mobile.
- Поддержка reduced motion.

### Этап 10. Реализация и регрессионная проверка
- Вносить изменения небольшими частями прямо в `main`.
- Проверять реальные пользовательские сценарии.
- Запускать typecheck, lint, tests и build.
- Проверять отсутствие изменений в административной зоне.

### Этап 11. Финальная приёмка
- Визуальная проверка всех пользовательских маршрутов.
- Проверка light/dark и размеров экранов.
- Проверка доступности и ошибок runtime.
- Сверка результата с утверждёнными референсами и дизайн-токенами.
- Документирование оставшихся ограничений.

## 6. Definition of Done

Экран считается завершённым только когда:
- соответствует утверждённому направлению и дизайн-системе;
- отражает реальные возможности продукта;
- все видимые действия имеют корректное поведение;
- предусмотрены loading, empty, error, success, disabled и permission states там, где они применимы;
- корректно работает на поддерживаемых размерах экрана;
- проверены light/dark темы;
- нет критических ошибок доступности и runtime;
- проходят релевантные проверки проекта;
- изменения находятся в `main` и проверены по diff.

## 7. Текущая очередь

1. Завершить этап 0 только по пользовательским маршрутам.
2. Зафиксировать карту пользовательских экранов и исходные ограничения.
3. Перейти к исследованию конкурентов.
4. Согласовать UX и дизайн-фундамент.
5. Только затем переходить к реализации пользовательских экранов.

Административная панель остаётся вне очереди до отдельного распоряжения пользователя.
