## Итог

NEXUM имеет значительную техническую основу: отдельные web/API приложения, AI Gateway/provider abstraction, агентский цикл, управление задачами, проектные инструменты, Docker Sandbox, runtime/checkpoint механизмы и E2E-тесты. Однако текущий `main` отстаёт от нескольких важных веток исправлений. На момент аудита несколько исправлений P0 находятся в открытом PR #35 и не являются частью `main`.

**Рекомендация:** приостановить добавление новых продуктовых функций до закрытия P0, привести CI к воспроизводимому состоянию, интегрировать проверенные исправления в правильном порядке и пройти сквозные сценарии на итоговом commit.

## Подтверждённые находки

### AUD-001 — внутренние диагностические маршруты доступны без middleware авторизации

**Severity:** P0  
**Статус:** подтверждено в `main`, исправление видно в PR #35.

В `apps/api/server.ts` следующие маршруты объявлены без `authMiddleware`:
- `POST /api/diagnostics/events`
- `GET /api/diagnostics/session/:sessionId`
- `GET /api/diagnostics/latest`
- `GET /api/runtime/status`

При этом они возвращают внутренние события, состояние задач/процессов и диагностику. Публичная запись событий также позволяет внешним запросам засорять диагностику. Защита этих маршрутов добавлена в PR #35.

**Что сделать:** интегрировать и проверить middleware в #35; убедиться, что события фильтруются по владельцу проекта/пользователю; добавить HTTP-тесты на 401 без сессии и ограниченный ответ с сессией.

### AUD-002 — исполнение команд агента в основной ветке запускается вне Docker Sandbox

**Severity:** P0  
**Статус:** подтверждено в `main`, исправление видно в PR #35.

В `apps/api/agent/tools/runCommand.ts` текущая реализация использует `spawn` для выполнения команд после allowlist-валидации. Allowlist и запрет shell-операторов снижают риск, но не являются изоляцией от кода проекта и lifecycle-скриптов зависимостей. PR #35 маршрутизирует исполняемые команды через `DockerSandbox` и очищает унаследованное окружение для git-команд.

**Что сделать:** проверить, что каждый исполняемый агентом build/test/Node-путь изолирован; протестировать попытки чтения env/host-файлов, доступа к сети, превышения CPU/RAM/PID, тайм-аутов, отмены и очистки контейнера. Проверить отдельно bootstrap зависимостей, поскольку установка пакетов требует контролируемого сетевого доступа.

### AUD-003 — зависимости node_modules закоммичены в репозиторий

**Severity:** P1  
**Статус:** подтверждено в `main`.

В дереве `main` обнаружено 1 799 записей, из них 1 570 путей внутри `apps/api/node_modules/`; там же tracked-файл `apps/api/node_modules/.package-lock.json`. Текущий `.gitignore` не исключает `node_modules`. PR #35 добавляет исключение и удаляет закоммиченные зависимости.

**Риски:** лишний объём репозитория, платформозависимые бинарники, шум в diff, расхождение установленных зависимостей с lock-файлом и затруднённое обновление пакетов.

**Что сделать:** принять удаление node_modules из PR #35, добавить игнорирование всех node_modules/dist, использовать `npm ci` в CI и Docker, убедиться, что lock-файлы — единственный источник восстановления зависимостей.

### AUD-004 — E2E CI не воспроизводим на текущем workflow main

**Severity:** P0/P1  
**Статус:** сильное подтверждение по конфигурации; точная причина последнего падения требует отчёта Playwright.

В запуске [CI 38146821629](https://github.com/borzenkoofficial-lab/nexum-dev/actions/runs/38146821629) build-job прошёл, а E2E упал на шаге `Run Runtime Phase 2.5 E2E`. В текущем `.github/workflows/ci.yml` на `main` нет шага загрузки Docker-образа `node:22-bookworm-slim`, тогда как `DockerSandbox` требует наличия Docker daemon и этого образа. В workflow PR #35 добавлен шаг `docker pull node:22-bookworm-slim`; на его commit CI прошёл, включая E2E.

Это указывает на вероятную причину: E2E-запуск из `main` не подготавливает sandbox-образ. Однако до чтения отчёта Playwright это остаётся обоснованной гипотезой, а не окончательно доказанным root cause.

**Что сделать:** интегрировать workflow из проверенной ветки, обеспечить подготовку образа и вывод причин падения, затем повторить E2E на финальном merge commit.

### AUD-005 — в main нет AnyModel provider, который есть в PR #35

**Severity:** P1  
**Статус:** подтверждено сравнением веток.

В `main` отсутствует `apps/api/ai/providers/anymodel.ts`, а корневой `.env.example` по умолчанию указывает на OpenRouter. PR #35 добавляет AnyModel provider, runtime-key handling и тесты провайдера.

**Что сделать:** после принятия PR #35 проверить реальный вызов API с временным ключом, список моделей, ошибки 401/403/429/5xx, тайм-ауты, отмену и отсутствие ключа в логах/клиентском коде. Не считать провайдер готовым только по unit-тесту с mock fetch.

### AUD-006 — текущий CI использует npm install для API вместо npm ci

**Severity:** P1  
**Статус:** подтверждено в workflow `main`.

Workflow `.github/workflows/ci.yml` использует `npm install --prefix apps/api`, а не строгое восстановление lock-файла. В PR #35 команда заменена на `npm ci`.

**Что сделать:** унифицировать воспроизводимую установку в CI и Docker; убедиться, что все lock-файлы синхронизированы с package.json.

### AUD-007 — API health сообщает сведения о провайдерах и статусах ключей без авторизации

**Severity:** P2  
**Статус:** подтверждено в `main`.

Маршрут `GET /api/health` возвращает имя AI provider, fallback и булевы признаки наличия некоторых ключей. Он может оставаться публичным для health checks, но ответ должен быть минимальным и не раскрывать внутреннюю конфигурацию.

**Что сделать:** разделить публичный liveness/readiness и внутреннюю диагностику; публичный ответ ограничить состоянием сервиса, а детальные сведения защищать авторизацией.

### AUD-008 — AI status endpoint не использует authMiddleware в main

**Severity:** P1  
**Статус:** подтверждено в просмотренном `apps/api/server.ts`; PR #35 добавляет middleware.

Маршрут `GET /api/ai/status` объявлен без явного `authMiddleware`, в отличие от соседних маршрутов `/api/ai/providers` и `/api/ai/models`.

**Что сделать:** защитить статус пользователя и провайдера; проверить, что ответ не выдаёт сведения о ключах или подключениях других пользователей.

### AUD-009 — ключевые P0-исправления не входят в main

**Severity:** P0  
**Статус:** подтверждено по состоянию веток.

PR #35 `fix(runtime): harden P0 execution and job lifecycle` оставался открытым при аудите, несмотря на успешный CI на его commit `ec653c06...`. Он содержит защиту diagnostics/runtime, sandbox execution, обработку отмены, сверку состояния проекта перед публикацией completed и ограничения cache.

**Что сделать:** провести review diff #35, проверить результаты CI на его HEAD, разрешить конфликты и объединить в main. После слияния запустить CI на новом main; не считать зелёный CI feature-ветки доказательством того, что main исправлен.

### AUD-010 — документация и статус готовности не отражают фактическую ветку

**Severity:** P1  
**Статус:** подтверждено.

README в `main` был минимальным, а новая документация находится в отдельном PR #37. Одновременно в репозитории есть несколько открытых веток/PR с существенными исправлениями и незавершёнными E2E/UI изменениями.

**Что сделать:** объединить документацию после проверки CI; вести статусы по фактическому коду и результатам тестов. Для каждого DONE фиксировать commit, команду проверки и ссылку на CI.

## Сквозные сценарии приёмки

Не выпускать продукт до прохождения следующих сценариев на одном и том же проверенном commit:

1. Создание нового пустого проекта → scaffold → генерация → build → тест → preview → Completion Gate.
2. Изменение существующего проекта без удаления/перезаписи несвязанных файлов.
3. Неудачная сборка не приводит к статусу completed.
4. Runtime-ошибка preview передаётся агенту, исправление выполняется ограниченно, проверка повторяется.
5. Отмена задачи останавливает модель и дочерние процессы; статус остаётся cancelled.
6. Перезапуск API не приводит к вечному running и не теряет критические данные задачи.
7. Два пользователя не могут прочитать файлы, проекты, diagnostics или AI credentials друг друга.
8. Недоступность провайдера и rate limit дают понятную ошибку, без бесконечных повторов.
9. Docker недоступен или образ отсутствует — система сообщает о блокере, а не имитирует успех.
10. Запросы к внутренним диагностическим endpoint без сессии получают 401/403.
