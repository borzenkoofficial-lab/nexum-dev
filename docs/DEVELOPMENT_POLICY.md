# КВАРД — правила разработки

## Единственная рабочая ветка

- Рабочая ветка продукта — `main`.
- Новые feature/fix/design/release branches не создавать.
- Новые Pull Request для штатной разработки не создавать.
- Изменения вносить непосредственно в `main` небольшими логическими коммитами.
- После каждого логического блока проверять актуальный HEAD, diff и доступные CI checks.
- Не выполнять массовые перезаписи файлов по устаревшим PR-патчам.

## Перенос незавершённых изменений

Старые ветки и Pull Request являются источниками для аудита, а не рабочими линиями разработки.

Перед переносом каждого изменения:
1. Проверить, не присутствует ли оно уже в `main`.
2. Проверить совместимость с текущими интерфейсами, миграциями, package scripts и runtime.
3. Переносить только необходимый функционал, тесты и документацию.
4. Изменять существующие миграции нельзя; новые миграции должны использовать следующий свободный номер и проверяться на повторный запуск.
5. Не переносить артефакты сборки, node_modules, секреты и конфигурацию окружений с приватными значениями.
6. Запустить подходящие тесты, typecheck и build. Если CI или внешняя проверка ещё не завершились, явно оставить результат непроверенным.

## Границы безопасности

- Не удалять старые ветки, пока их уникальные изменения не сверены с `main`.
- Не удалять пользовательские данные и не выполнять production migrations без отдельной процедуры подтверждения/резервирования.
- Не сливать PR и не запускать production deployment: штатная разработка уже ведётся прямо в `main`.
- Не объявлять feature готовой только по факту наличия файлов; нужны тесты и подтверждение реального поведения.

## Приоритеты продукта

1. Надёжность существующего Builder: задача → план → инструменты → сборка → проверка → подтверждённое завершение.
2. Безопасность исполнения, sandbox и tenant isolation.
3. Постоянное хранение проектов и файлов.
4. Универсальные бизнес-агенты: версии, инструменты, approval, знания и память.
5. Durable queue/workers, lease renewal, recovery, idempotency и cancellation fencing.
6. Credentials, usage limits, billing, observability.
7. Единая дизайн-система и UX.
8. Production readiness и коммерческий запуск.

Обновлять этот документ при изменении правил. Проверять текущее состояние GitHub и кода в каждом новом рабочем сеансе.
