# КВАРД Studio — UX-спецификация Builder

Дата: 2026-11-25
База: main `adb873444b022bf830a2c291e3adca6d9a9445d7`
Направление: Balanced
Статус: концепция пользовательского интерфейса; реализация не начата

## 1. Назначение

Project Studio — основная рабочая поверхность КВАРД. Пользователь формулирует задачу, взаимодействует с AI-агентом, наблюдает ход работы, проверяет результат и при необходимости открывает файлы или код. Интерфейс должен сохранять контекст проекта и не маскировать ограничения backend.

## 2. Проверенное текущее устройство

Исходники на указанном HEAD:
- `BuilderShell.tsx`: шапка проекта, вкладки Preview / AI-агент / Файлы / Код, статус, интеграции, копирование ссылки, открытие Preview.
- `BuilderChat.tsx`: история сообщений, composer, вложения, выбор провайдера и модели, отправка, остановка, повтор задачи, быстрые действия.
- `BuilderTools.tsx`: Preview, список и просмотр файлов, адаптивные размеры устройств, ход выполнения агента, этапы, проблемы и план продукта.
- `BuilderCode.tsx`: отдельный редактор файлов с сохранением.
- `builder.css`: отдельные scoped-стили Studio; semantic tokens подключены из `kvard-design-system.css`.

Это не новая функциональная модель: спецификация упорядочивает существующие сценарии и определяет визуальную иерархию. Перед любым кодовым изменением повторно проверить HEAD и содержимое каждого файла.

## 3. Принцип композиции

### Desktop
- Шапка проекта остаётся компактной и фиксированной: возврат в рабочую среду, имя проекта, статус, основные инструменты и контекстные действия.
- Основная область делится на две рабочие зоны: диалог/управление задачей и результат.
- Рекомендуемая стартовая пропорция: левая зона 38–42%, правая 58–62%; обе имеют независимую прокрутку. Это проектное значение для проверки на реальном экране, не жёсткий контракт.
- В правой зоне сохраняются режимы Preview, ход агента, Files и Code. Переключение не должно сбрасывать сообщения, выбранную модель, задачу или контекст проекта.
- Composer закреплён внизу зоны диалога, растёт по содержимому в разумных пределах; вложения и выбор модели не должны перекрывать поле ввода.
- Preview занимает максимум доступной площади. Панель устройства (desktop/tablet/mobile), обновление и состояние доступности размещаются в его верхней панели.

### Tablet
- Сохраняется двухпанельная компоновка, если ширины достаточно.
- При нехватке ширины переходить на переключаемые панели Chat и Result, а не сжимать обе до нечитаемого состояния.
- Все ключевые действия остаются доступны без hover.

### Mobile
- Одна основная панель за раз: Chat / Preview / Agent / Files.
- Панель навигации инструментов становится горизонтальной прокручиваемой полосой или компактным переключателем.
- Composer и кнопка остановки остаются доступными в нижней части экрана.
- Действия интеграции/копирования ссылки не должны вытеснять основную задачу; допускается контекстное меню.
- Файловая навигация не должна фиксировать широкую desktop-колонку.

## 4. Визуальная иерархия

- Balanced: спокойные поверхности, ясные границы зон, контролируемый акцент, умеренная плотность.
- Основной фон — canvas; рабочие панели — surface; вложенные панели — subtle surface; разделители — semantic border.
- Фиолетовый action применяется к первичному действию и текущему активному состоянию, не к каждому элементу.
- Статусы имеют текст и иконографию/маркер; цвет не является единственным носителем значения.
- Системные шрифты и типографическая шкала берутся из общей дизайн-системы. Не вводить отдельные несогласованные размеры только для Builder.
- Радиусы и тени использовать через существующие semantic tokens; не добавлять декоративное свечение, glassmorphism и крупные градиенты.

## 5. Поведение и состояния

### Composer
- Enter отправляет, Shift+Enter добавляет строку.
- Пока задача выполняется, поле и выбор модели блокируются согласно текущему контракту; остановка доступна отдельным действием.
- Вложения отображаются до отправки и могут быть удалены.
- Ошибка отправки не должна терять текст и вложения.
- Пустой ввод не отправляется.

### Agent lifecycle
Отображать только состояния, которые реально подтверждены runtime:
- анализ;
- планирование;
- ожидание подтверждения;
- разработка;
- проверка;
- завершено;
- ошибка;
- отменено/остановлено, если это состояние подтверждается backend.

У каждого состояния показывать краткое объяснение и доступное действие. Не имитировать прогресс или живую активность, если runtime не прислал соответствующие события.

### Preview
- Различать Preview online/offline и опубликованный production URL; не называть preview production.
- Пустое состояние объясняет, почему Preview пока недоступен и что пользователь может сделать.
- Ошибка загрузки имеет retry, если такой retry поддержан текущим API.
- Переключение размеров устройства меняет только viewport, а не проект.

### Files / Code
- Показывать загрузку, пустой список, ошибку, выбранный файл и несохранённые изменения.
- При переходе от файла с несохранёнными изменениями запросить подтверждение или сохранить черновик; не терять содержимое.
- Save disabled, когда нет изменений или идёт сохранение.
- После успешного сохранения показывать подтверждённое состояние, а не оптимистичную фикцию.

### Plan / approvals / problems
- План агента отделять от фактического выполнения.
- Ожидание подтверждения визуально и по действию отличается от обычного статуса «выполняется».
- Проблемы показывать списком с понятным контекстом; Repair доступен только если подключён рабочий обработчик.
- Retry, Cancel и Repair — разные операции, не объединять их в одну кнопку.

## 6. Референсы и переносимые паттерны

- Lovable: диалог и Preview в одном поле зрения; контекстные визуальные правки прямо в Preview — перспективное развитие, не заявлять как существующую функцию КВАРД.
  - https://lovable.dev/build/app-builder
  - https://lovable.dev/blog/introducing-visual-edits
- Replit Agent task board: явные Draft / Active / Ready / Done и проверка результата перед применением. Для КВАРД взять ясность этапов, но не переносить изолированные worktree/ветки, так как workflow проекта требует main-only.
  - https://docs.replit.com/references/agent/task-board
- Cursor Design Mode: выбор элемента/области в работающем Preview и передача контекста агенту. Рассматривать как отдельную будущую возможность после стабилизации базового Builder.
  - https://cursor.com/docs/agent/design-mode
- Cursor Agent: прозрачность diff и возможность остановить агента. Переносить принцип review/stop, не копировать агентную инфраструктуру.
  - https://cursor.com/help/ai-features/agent

## 7. Что не входит в текущую реализацию

- Визуальный выбор DOM-элемента и отправка аннотаций агенту.
- Мультиагентная параллельная работа и worktrees.
- Полноценная система версий/отката, если её нет в backend.
- Автоматический деплой или production promotion, если операция не поддержана реальным API.
- Новые API, миграции, изменение авторизации или прав.
- Любые изменения административной панели.

## 8. Критерии приёмки дизайна

- Пользователь всегда понимает, какой проект открыт и какую задачу выполняет агент.
- Chat и Preview доступны без потери контекста.
- Все статусы и метрики основаны на реальных данных.
- Ошибка, ожидание подтверждения, выполнение, завершение и отмена визуально различимы.
- Нет горизонтального переполнения на 320 px.
- Tablet не превращает две панели в узкие нечитаемые колонки.
- Клавиатурная навигация и focus-visible сохранены.
- Проверены light и dark themes.
- Не затронуты бизнес-логика, API, авторизация, роли и административные файлы.

## 9. Ограничения текущей проверки

Проверены исходники и стили на указанном commit. Визуальный runtime-аудит на реальном браузере не выполнен. Доли панелей и адаптивные переходы — предложения для последующей проверки, а не утверждение о текущем поведении.
