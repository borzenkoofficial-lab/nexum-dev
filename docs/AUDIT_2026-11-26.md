## 7. Биллинг Builder v1 (2026-11-26)

Решение владельца: цены придумать временно, поменяем потом.

- Тарифы — `apps/api/billing/builderPlans.ts`, **PLACEHOLDER**: Free 0 ₽ (15 задач, 300k токенов, 1 параллельно), Start 990 ₽ (150 / 3M / 2), Pro 2 990 ₽ (600 / 12M / 3), Team 9 990 ₽ (3 000 / 60M / 6) в месяц. Внутренний план `dev` используется вне production по умолчанию и запрещён как production default.
- Жизненный цикл: `reserve` до создания задачи (402 + код `TASK_LIMIT` / `TOKEN_LIMIT` / `PARALLEL_LIMIT`), `settle` по завершении запущенного AgentLoop (success, failure и cancel — расход провайдера уже был), `release`, если AgentLoop не стартовал (lock, persistence, ошибка до dispatch).
- Атомарность: в PostgreSQL — `SELECT … FOR UPDATE` строки аккаунта сериализует резервы одного пользователя. `settle`/`release` меняют только строку `reserved`, поэтому двойное списание и возврат после списания невозможны. Зависший резерв (>2 ч, процесс упал) списывается по полному резерву — в сторону переучёта, не недоучёта.
- Миграция `020_builder_billing.sql` только добавляет таблицы, повторный запуск — no-op (проверено).
- API: `GET /api/billing/builder` — сводка периода (`pricingIsPlaceholder: true`).
- Тесты: `billing/builderBilling.test.ts` — 11/11, включая конкурентные резервы на живом PostgreSQL (`KVARD_TEST_DATABASE_URL`). Без этой переменной PostgreSQL-тест пропускается, в CI он сейчас не запускается.
- UI (2026-11-27): «Настройки → Тариф и лимиты» (`BillingUsageSection`): тариф, цена, задачи и токены за месяц с индикаторами, дата сброса, параллельные задачи, пометка о предварительных ценах; состояния загрузки и ошибки с повтором. Проверено скриншотами (светлая/тёмная тема, 390 px — без горизонтального скролла).
- Фактический usage (2026-11-27): gateway передаёт `onUsage` после каждой генерации — только usage с меткой `provider_reported` (стрим-событие `usage` или `AIResponse.usageSource`). Оценки и legacy-провайдеры дают `null`. `JobUsageMeter` списывает фактические **выходные** токены, только если каждый вызов из token budget был учтён и у всех есть usage провайдера; иначе остаётся верхняя граница. Ledger хранит `input_tokens`/`output_tokens` отдельно от `billed_tokens` (`024`). Ограничение: mock-провайдер usage не сообщает, поэтому путь `provider_reported` проверен только юнит-тестами, на реальном провайдере — нет (нет ключа).
- Не сделано: назначение плана (смена тарифа), оплата, стоимость sandbox, перевод токенов в деньги (себестоимость по моделям).

## 9. Security review, часть 2 — вход и сессии (2026-11-27)

Проверено по коду: пароли — scrypt (соль 16 байт, `timingSafeEqual`), 8–128 символов. Cookie `HttpOnly; SameSite=Lax; Secure` (в production). MFA (TOTP) для админов, challenge-cookie `SameSite=Strict` на отдельном пути.

| Находка | Исправление |
|---|---|
