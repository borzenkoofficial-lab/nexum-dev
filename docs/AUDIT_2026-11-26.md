## 3. Техническая карта (по коду)

- **apps/api** — Node 22, Express 5, TypeScript, `pg`. Монолитный `server.ts` (~2000 строк, 55 маршрутов) и роутеры `routes/*`. 19 SQL-миграций (`db/migrations`, `db:migrate`).
  - Auth: `auth.ts` — сессионная cookie `HttpOnly; SameSite=Lax; Path=/`, `Secure` в production. В production отключить auth нельзя (процесс падает). MFA для админов (TOTP, отдельная cookie `SameSite=Strict` на `/api/auth/admin-mfa`).
  - Все пользовательские префиксы (`/api/projects`, `/api/chat`, `/api/agents`, `/api/preview`, `/api/organizations`, `/api/runtime/status`, …) закрыты `authMiddleware` через `app.use`. Без auth открыты только `health`, `build-info`, `auth/register|login|logout`. `/api/test/agent-failures` существует только при `NODE_ENV !== production` и включённом failure injection.
  - CORS: в production — allowlist из `NEXUM_CORS_ORIGINS`, `credentials: true`, wildcard не используется. Вне production — `origin: true`.
  - AgentLoop (`agent/loop.ts`, ~1700 строк): DAG шагов плана, completion gate, adaptive token budget, action journal, зашифрованные checkpoint (`KVARD_AGENT_CHECKPOINT_ENCRYPTION_KEY`), approvals.
  - ChatJob: хранилище в Postgres либо в памяти без `NEXUM_DATABASE_URL`. SSE `/api/chat/jobs/:id/events` с polling, heartbeat и backpressure.
  - AI: единый gateway и адаптеры (openai, anthropic, openrouter, anymodel, orcarouter, ollama, mock), conformance-тесты контракта.
  - Sandbox: `docker` (только вне production) и `daytona` (`@daytona/sdk` 2.1.0). В production провайдер нужно задать явно (`NEXUM_SANDBOX_PROVIDER=daytona`), иначе исполнение запрещено.
- **apps/web** — React 19, Vite 8. Builder встроен в SPA, `App.tsx` ~1600 строк. Отдельного `apps/studio` пока нет: архитектура описана в `docs/KVARD_STUDIO_ARCHITECTURE.md`, чек-лист не выполнен.
- **e2e** — Playwright 1.63, 45 сценариев (агент, отмена, approvals, runtime, preview, reconnect, responsive).
- **Deploy** — `Dockerfile` (multi-stage), `docker-compose.yml` + `deploy/timeweb/Caddyfile` (Caddy TLS reverse proxy), `scripts/deploy-timeweb.sh`, `vercel.json` (только SPA preview), `render.yaml` (устаревшая конфигурация).

## 7. Биллинг Builder v1 (2026-11-26)

Решение владельца: цены придумать временно, поменяем потом.

- Тарифы — `apps/api/billing/builderPlans.ts`, **PLACEHOLDER**: Free 0 ₽ (15 задач, 300k токенов, 1 параллельно), Start 990 ₽ (150 / 3M / 2), Pro 2 990 ₽ (600 / 12M / 3), Team 9 990 ₽ (3 000 / 60M / 6) в месяц. Внутренний план `dev` используется вне production по умолчанию и запрещён как production default.
- Жизненный цикл: `reserve` до создания задачи (402 + код `TASK_LIMIT` / `TOKEN_LIMIT` / `PARALLEL_LIMIT`), `settle` по завершении запущенного AgentLoop (success, failure и cancel — расход провайдера уже был), `release`, если AgentLoop не стартовал (lock, persistence, ошибка до dispatch).
- Атомарность: в PostgreSQL — `SELECT … FOR UPDATE` строки аккаунта сериализует резервы одного пользователя. `settle`/`release` меняют только строку `reserved`, поэтому двойное списание и возврат после списания невозможны. Зависший резерв (>2 ч, процесс упал) списывается по полному резерву — в сторону переучёта, не недоучёта.
- Миграция `020_builder_billing.sql` только добавляет таблицы, повторный запуск — no-op (проверено).
- API: `GET /api/billing/builder` — сводка периода (`pricingIsPlaceholder: true`).
- Тесты: `billing/builderBilling.test.ts` — 11/11, включая конкурентные резервы на живом PostgreSQL (`KVARD_BILLING_TEST_DATABASE_URL`). Без этой переменной PostgreSQL-тест пропускается, в CI он сейчас не запускается.
- Не сделано: UI-экран тарифа/остатка, назначение плана (смена тарифа), оплата, учёт фактического usage провайдера и стоимости sandbox.
