# Durable project workspace storage

Status: architecture foundation; runtime cutover is intentionally not part of this change.

## Current failure mode

The current `ProjectManager` stores project metadata in `.nexum-projects.json` and source files under `runtime/users/<userId>/projects`. Both are local container filesystem state. A redeploy can discard it, and two API replicas do not share it. The in-memory `projectManagers` cache also means local metadata is not coordinated across replicas.

## Target architecture

- PostgreSQL is authoritative for workspace identity, owner, display metadata, active project, committed revision, and file manifest.
- S3-compatible object storage (AWS S3, Cloudflare R2, or another compatible provider) stores immutable file objects and immutable revision manifests.
- API/worker processes materialize a project revision into a private, per-job local workspace because current Builder tools, Git, preview, build, and sandbox adapters require POSIX paths.
- A project lease prevents two writers from materializing and committing the same workspace concurrently. Existing project locks are the starting point, but their semantics must be verified for all routes and worker processes before cutover.
- A write is committed by uploading changed immutable objects, uploading a manifest, and atomically advancing the PostgreSQL committed revision in a transaction. Readers continue to see the previous revision until that transaction succeeds.
- Unreferenced objects are garbage-collected only after a retention window. Never delete objects as part of the commit path.

## Object namespace

Object keys are generated by the server and scoped as:

`workspaces/<opaque-user-namespace>/<opaque-workspace-id>/revisions/<revision>/<sha256>`

Do not derive bucket keys directly from untrusted user paths. Store the validated relative path in the PostgreSQL manifest and map it to an opaque object key. Bucket access is private; the browser never receives permanent bucket credentials.

## Path and content policy

- Reject absolute paths, empty segments, `.`, `..`, backslashes, NUL bytes, and symlinks.
- Normalize separators before validation; validate again after decoding URL input.
- Exclude `.env*`, credentials, `.git`, `node_modules`, caches, and generated build output from snapshots by default. Exceptions must be explicit and reviewed.
- Enforce per-file, per-workspace, file-count, and total upload limits on the server.
- Calculate SHA-256 server-side; never trust a client-supplied hash.
- Apply tenant checks to every workspace query and object operation.

## Rollout plan

1. Apply the metadata schema only; it does not change runtime behavior.
2. Add and test the S3-compatible object adapter and local adapter contract.
3. Add a manifest repository with optimistic revision checks and transactional commit.
4. Add safe materialize/commit lifecycle around Builder jobs and all mutating project routes.
5. Add a dry-run importer that inventories existing local workspaces and reports conflicts without changing source data.
6. Run restart, two-replica, concurrent-writer, interruption, quota, and tenant-isolation tests against an isolated S3-compatible test service.
7. Enable storage per environment behind an explicit provider flag. Production must fail readiness when S3 is selected but credentials/bucket are missing; never silently fall back to ephemeral disk.
8. Migrate existing projects with checksums and a reversible cutover window. Keep old local data until restore verification passes.

## Operational requirements

- Use server-side credentials with bucket-scoped least privilege.
- Require TLS and private bucket policy.
- Configure object versioning or immutable revision keys, lifecycle retention, and independent backups.
- Emit metrics for materialization duration, upload bytes, commit latency, failed commits, stale leases, orphan objects, and restore tests.
- Document credential rotation, backup restore, regional outage behavior, and provider migration.

## Schema introduced in this phase

- `project_workspaces`: owner, project identity, storage namespace, lifecycle state, committed revision.
- `project_workspace_files`: current committed file manifest and checksums.
- `project_workspace_commits`: immutable revision manifest records.
- `user_project_settings`: active project selection persisted per user.

The schema is deliberately additive. Existing `ProjectManager` remains the active runtime implementation until the storage adapter, manifest transaction, migration tooling, and end-to-end lifecycle are all verified.
