# КВАРД — исследование пользовательских интерфейсов конкурентов

Дата: 2026-11-25  
Направление КВАРД: Balanced  
Статус: исследование выполнено по официальным продуктовым страницам, документации, changelog и опубликованным интерфейсным изображениям. Это не usability-тест закрытых аккаунтов конкурентов.

## 1. Цель и рамки

Изучаем не «красивые картинки», а конкретные интерфейсные решения, которые помогают пользователю:
- начать работу с идеей;
- управлять проектом и контекстом;
- взаимодействовать с AI-агентом;
- видеть, что агент делает и что изменил;
- проверять результат в Preview;
- управлять интеграциями и публикацией;
- быстро ориентироваться в продукте.

Административные панели конкурентов не переносим в текущий scope КВАРД. Исследование касается только пользовательских поверхностей.

## 4. Выводы для КВАРД

### 4.1 Единая оболочка, но разные рабочие режимы

Не нужно заставлять все разделы выглядеть как один и тот же экран. Нужна единая оболочка и дизайн-грамматика, но различная композиция по задаче:
- Overview — стартовая точка и недавние проекты;
- Studio — плотная рабочая поверхность;
- AI Agents — каталог, настройки и runtime;
- Business Agents — управление агентами, знаниями, командами и согласованиями;
- Integrations — каталог подключений и статусы;
- Diagnostics — техническая хронология;
- Settings — категории и формы настроек.

### 4.2 Builder должен быть центром продукта

Рекомендуемая основа:
- центр тяжести — текущий результат и работа с ним;
- диалог агента всегда доступен, но не должен поглощать всё пространство;
- Preview, Files, Code и Agent — переключаемые инструменты с сохранением контекста;
- агентский план и текущий этап выполнения должны быть видимы без длинного технического лога;
- ошибки, ожидание подтверждения, отмена и повторный запуск должны быть разными состояниями;
- пользователь должен понимать, где Preview, а где опубликованный production-результат.

### 4.3 Визуальный контроль важнее декоративной анимации

Наиболее сильная идея из Lovable и Cursor — не эффектная анимация, а точное указание на элемент интерфейса и передача контекста агенту. Для КВАРД это перспективный следующий слой после стабилизации Builder:
1. выбрать элемент в Preview;
2. приложить селектор, компонентный контекст и снимок;
3. сформулировать изменение;
4. показать план;
5. применить и показать diff/результат.

Это предложение на будущее, а не утверждение, что такая функция уже реализована.

### 4.4 Агентские статусы должны быть операционными

Заимствовать ясность статусов и этапов из Cursor/Replit, но оставить только состояния, которые действительно возвращает Runtime. Минимальный словарь:
- Черновик;
- Ожидает запуска;
- В очереди;
- Планирует;
- Выполняет;
- Ожидает подтверждения;
- Завершён;
- Ошибка;
- Отменён.

У каждого состояния должны быть timestamp, контекст задачи и доступное пользователю следующее действие. Не использовать «живые» точки/пульсации без реального события.

### 4.5 Главная должна начинать работу, а не быть витриной виджетов

Сохранить быстрый ввод задачи и последние проекты. Не добавлять искусственные метрики и декоративные дашборд-карточки. Сводка полезна только тогда, когда отвечает на вопрос: «Что я делал, что происходит и куда перейти дальше?»

### 4.6 Навигация и типографика

Применить Linear/Vercel:
- один предсказуемый sidebar;
- единая высота и логика заголовков;
- стабильные breadcrumbs/context labels;
- умеренная плотность и контраст между навигацией и рабочей областью;
- одинаковые состояния hover/focus/active/disabled;
- командная палитра и горячие клавиши как ускорители, а не замена видимой навигации.

## 5. Предлагаемая композиция пользовательской системы

Это функциональная схема, не финальный пиксельный макет:

```text
КВАРД
├── Global shell
│   ├── Brand + workspace context
│   ├── Primary navigation
│   ├── Project switcher / recent projects
│   ├── Search / command palette
│   └── Account / notifications
│
├── Overview
│   ├── Main task composer
│   ├── Recent projects
│   └── Recent activity (only real events)
│
├── Project Studio
│   ├── Project header + status
│   ├── Agent conversation / task plan
│   ├── Result preview
│   ├── Files / Code / Agent tools
│   ├── Diff / approval / recovery states
│   └── Preview vs Production distinction
│
└── Product areas
    ├── AI Agents
    ├── Business Agents
    ├── Integrations
    ├── Diagnostics
    ├── Journal
    └── Settings
```

## 6. Рекомендация по выбору визуального направления

Сохраняем утверждённый Balanced. Не копируем одну платформу целиком.

Распределение ролей:
- **Vercel** — структура навигации и проектного контекста.
- **Lovable** — Builder: чат и результат в одном поле зрения.
- **Replit Agent 4** — планирование и работа с визуальными артефактами.
- **Cursor 3** — прозрачность агентских сессий, diff и визуальная аннотация.
- **Linear** — консистентность, типографика, sidebar и сканируемость.
- **Stripe** — ясные overview и честное представление метрик.

Рекомендуемая итоговая формула: **Vercel clarity + Lovable interaction + Cursor agent transparency + Linear consistency**, с выборочными паттернами Replit для визуальной работы и без копирования тяжёлого IDE-хрома.

## 7. Что не переносим

- Не переносим OS/Desktop metaphor в каждый экран: пользователь пришёл работать с проектом, а не симулировать операционную систему.
- Не добавляем 3D, стекло, неон, свечения или motion ради визуального эффекта.
- Не показываем фиктивные deployment, AI usage, agent health, connected integrations или финансовые метрики.
- Не заставляем пользователя проходить длинную загрузочную анимацию.
- Не вводим параллельные worktrees/ветки как обязательный процесс разработки КВАРД: работа в репозитории ведётся в `main` по прямому требованию пользователя.
- Не дублируем управление в нескольких панелях.
- Не прячем основные действия исключительно в hover или командную палитру.

## 8. Приоритеты следующего проектного этапа

1. Утвердить карту оболочки и Studio.
2. Зафиксировать точную композицию главной и Studio.
3. Подготовить подборку из 2–3 референсов на каждый ключевой экран.
4. Утвердить визуальные токены после сверки с текущими CSS.
5. Только после этого начинать реализацию небольшими коммитами прямо в `main`.
