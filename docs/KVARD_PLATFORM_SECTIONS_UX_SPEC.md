# КВАРД — UX-спецификация интеграций, диагностики, журнала, настроек и авторизации

**Статус:** UX-аудит и спецификация, не реализация  
**Дата аудита:** 25 ноября 2026  
**Проверенная база:** `main` — `1361eafc6f1d4f69f127e963d43b5c465dd6c711`  
**Визуальное направление:** Balanced  
**Область:** пользовательская часть приложения. Административная панель, admin API, admin MFA, роли и права администраторов исключены.

---

## 1. Цель этапа

Согласовать пользовательские экраны, которые окружают основную рабочую среду:

- интеграции и подключение AI-провайдеров;
- диагностика и журнал действий;
- журнал продукта / новости;
- пользовательские настройки;
- вход и регистрация обычного пользователя.

Главный принцип: экран должен различать реальные подключённые сервисы, локальные предпочтения, временные runtime-состояния и ещё не реализованные возможности. Нельзя выдавать демонстрационную карточку за подключённую интеграцию, статическую запись за релиз или локальное состояние за серверную настройку аккаунта.

## 2. Проверенная текущая структура

- `apps/web/src/App.tsx` — маршрутизация, настройки, модальные окна интеграций, провайдеры и основной workspace.
- `apps/web/src/components/IntegrationPage.tsx` — каталог интеграций.
- `apps/web/src/components/DiagnosticsPage.tsx` — диагностика задач и событий.
- `apps/web/src/components/NewsPage.tsx` — статический журнал продукта.
- `apps/web/src/auth/AuthGate.tsx` — существующий login/register/MFA gate.

- `apps/api/server.ts` — auth, AI provider, diagnostics, runtime и project endpoints.
- `apps/api/auth.ts` — серверная сессия и проверка пользователя.
- `apps/api/diagnostics.ts` — хранение браузерных diagnostic sessions в памяти процесса.

## 3. Интеграции

### 3.1 Фактическое состояние

Экран `/connectors` показывает статические карточки:

**AI providers / local models**
- OpenAI
- Ollama
- OrcaRouter

**External services**
- GitHub
- Supabase
- Telegram

В `App.tsx` переменная `connectedConnectors` всегда равна пустому массиву. Кнопки карточек вызывают `ConnectorModal`, который прямо сообщает, что серверное подключение не реализовано, OAuth/API credentials не создаются и не сохраняются. Следовательно, на текущем экране не может появиться реальный connected state.

При этом реальное подключение AI provider key реализовано отдельно в Settings через `POST /api/ai/connect-key`; доступны runtime gateways для OpenAI, AnyModel, OrcaRouter и OpenRouter. Список провайдеров и моделей выдаётся через `GET /api/ai/providers` и `GET /api/ai/models`; доступность проверяется через `GET /api/ai/status`. Ollama и Anthropic также представлены на серверном gateway, но пользовательская форма ввода ключа/настройки для всех провайдеров пока не унифицирована.

**Хранение credentials:** `userAIGateways` — серверный in-memory Map по userId. Ключ не попадает в web bundle, но пользовательское подключение не является постоянным: Map теряется при перезапуске процесса. API key status также отражает текущий runtime gateway, а не долговременную запись в аккаунте.

### 3.2 UX-направление

Раздел должен стать реестром подключений с честным разделением двух типов:

1. **AI-провайдеры** — провайдер, модель, проверка доступности, способ хранения ключа, последний результат проверки.
2. **Интеграции сервисов** — GitHub, Supabase, Telegram и будущие сервисы. Показывать OAuth/API connection только после появления настоящего backend adapter, безопасного хранения credentials, callback/refresh и endpoint статуса.

Предлагаемая структура карточки:
- имя сервиса и назначение;
- фактический статус: подключено / не подключено / требуется повторная авторизация / проверка / временно недоступно / недоступно в текущей версии;
- область действия: личный аккаунт / проект / организация;
- безопасный набор доступных действий;
- дата последней успешной проверки, если сервер её возвращает.

В деталях AI-провайдера:
- выбрать провайдера и модель;
- добавить/заменить ключ через password input;
- проверить ключ на сервере;
- показывать маскированный fingerprint/последние символы только если backend возвращает безопасное представление;
- объяснить, что подключение сейчас действует только в памяти сервера и может сброситься при перезапуске;
- не показывать секрет повторно и не хранить его в localStorage/sessionStorage.

### 3.3 Запрещённые UX-обещания до backend-реализации

- Нельзя показывать GitHub/Supabase/Telegram как connected.
- Нельзя добавлять кнопки «Синхронизировать», «Отключить», «Управлять OAuth», если за ними нет реальных API.
- Нельзя говорить «ключ сохранён в аккаунте» или «подключение постоянное».
- Нельзя подменять отсутствие проверки статусом «Готово».
- Не добавлять список интеграций только ради наполнения каталога.

## 4. Диагностика

### 4.1 Фактические источники данных

На экране `/diagnostics` используются два разных потока:

**A. Agent job history**
- `GET /api/agent/diagnostics?limit=50`
- Данные берутся из `AgentHistory`, файл `runtime/agent-history.jsonl`.
- API фильтрует записи по project IDs текущего пользователя.
- Возвращаются recent entries, failures и последние 20 chat jobs.
- `AgentHistory.recent()` читает JSONL-файл и возвращает последние записи; это не полноценная база событий с пагинацией и retention policy.

**B. Chat job details**
- `GET /api/chat/jobs/:id`
- Показывает события, проблемы и ошибку конкретной задачи.

Дополнительный браузерный diagnostics pipeline:
- `POST /api/diagnostics/events` — session-start, app-mounted, console errors/warnings, fetch errors, runtime errors, workspace-context.
- `GET /api/diagnostics/session/:sessionId` и `GET /api/diagnostics/latest`.
- `apps/api/diagnostics.ts` хранит эти события в памяти процесса: максимум 50 сессий, до 500 событий на сессию.
- Чувствительные ключи и bearer tokens проходят базовую redaction в metadata/message.
- Это отдельный источник от AgentHistory; текущий экран DiagnosticsPage его напрямую не показывает.

### 4.2 UX-направление

Сделать экран инструментом поиска причины проблемы, а не панелью случайных чисел.

Рекомендуемая композиция:

1. Заголовок, последнее успешное обновление и действие Refresh.
2. Верхняя строка фактических сводных показателей: задания, ошибки, события, время обновления. Показатели должны явно иметь одинаковый временной/выборочный диапазон.
3. Левая колонка — список задач с реальным status, ID, временем и проектом.
4. Центральная колонка — хронология событий выбранной задачи.
5. Правая панель / drawer — подробности события: тип, время, tool, request/job/project IDs, duration, безопасные metadata, error code.
6. Фильтры: все / ошибки / задания; дополнительные фильтры по проекту и диапазону дат — только после поддержки query API.
7. Экспорт JSON сохраняется как реальная функция; перед экспортом объяснять, какие данные попадут в файл, и редактировать чувствительные значения.

Отдельно показать источник и retention:
- «История Agent — локальный JSONL на сервере».
- «Браузерные диагностические события — временное серверное хранилище; могут исчезнуть при перезапуске».
- Не смешивать два источника в одну временную шкалу без метки origin.

### 4.3 Важные ограничения

- Текущий DiagnosticsPage использует ограниченную выборку последних 50 событий и последних 20 jobs.
- Карточки сводных показателей показывают количество в этой выборке, а не lifetime totals.
- Временное хранилище browser diagnostics не должно называться постоянным журналом.
- События могут содержать технические детали и пути; подробности должны быть безопасно отформатированы и не раскрывать credentials.
- Экспорт — чувствительная операция: JSON может содержать сообщения, project IDs, job IDs и metadata. Не добавлять автоматическую публикацию/отправку экспорта.
- Статус API/runtime не должен подменяться статическим «Система готова» в оконной оболочке.

## 5. Журнал продукта / News

### 5.1 Фактическое состояние

`NewsPage.tsx` содержит массив из 14 hardcoded chapters. Даты — 25–28 сентября 2026 и «Сентябрь 2026». Источник данных — frontend code; endpoint релизов/новостей не обнаружен.

Это редакционная хронология, а не live feed, не release notes API и не changelog из Git. В тексте некоторые архитектурные направления описаны как уже состоявшиеся этапы, хотя по состоянию на ноябрь 2026 требуется перепроверить их фактическую готовность.

### 5.2 UX-направление

Переименовать раздел в **«Журнал КВАРД»** и разделить контент на типы:
- Релизы — только реально поставленные изменения с версией/датой/ссылкой на подтверждённый коммит или deployment.
- Разработка — редакционные заметки о направлении продукта, явно помеченные как заметки/эксперименты.
- Изменения — подтверждённый список пользовательских изменений.

Каждая запись:
- дата и тип публикации;
- заголовок и короткое описание;
- что изменилось для пользователя;
- статус: выпущено / эксперимент / планируется;
- ссылка на подробности или релевантную версию, если существует.

Не делать автоматически generated changelog, пока не создан надёжный pipeline, который связывает commit → release/deploy → пользовательское описание.

### 5.3 Редакционная точность

- Проверить все 14 существующих записей на предмет соответствия текущему состоянию.
- Сохранить полезную историю как архивные заметки, если даты и содержание подтверждаются.
- Не менять дату публикации на сегодняшнюю без фактического основания.
- Будущие функции не описывать в прошедшем времени.
- Не использовать фальшивые версии, метрики, количество пользователей или deployment status.

## 6. Настройки

### 6.1 Фактические категории и хранение

Текущая Settings страница находится inline в `App.tsx`.

Подтверждённые пользовательские параметры:
- Тема light/dark — `localStorage: kvard:theme`.
- Масштаб 90/100/110%.
- Compact mode.
- Animations on/off.
- Auto-preview.
- Sound notifications.
- AI provider/model selection.
- AI API key connection flows.
- Project count and local state description.
- Keyboard shortcut reference.
- AnyModel API key form.
- Local OpenRouter test session form.

Большинство UI preferences хранится в `localStorage: nexum:ui-settings`. Тема хранится отдельно. Некоторые параметры применяются к document root через data attributes. Это настройки текущего браузера/устройства, не серверного аккаунта.

AI provider/model selection в основном управляет текущим runtime состоянием клиента; пользовательские gateways с ключами хранятся на сервере в памяти процесса. Это не следует визуально объединять с локальными UI preferences.

Есть экспериментальная OpenRouter local test форма (`localAITestEnabled = true`) и отдельный AnyModel connection flow. Необходимо проверить необходимость обеих поверхностей и убрать дублирование только после технической проверки, не удаляя рабочие сценарии.

### 6.2 UX-направление

Сгруппировать настройки по понятным областям:

1. **Внешний вид** — тема, системная/светлая/тёмная тема (system only после поддержки), масштаб, плотность, motion.
2. **Рабочая среда** — auto-preview, параметры проекта, горячие клавиши.
3. **Уведомления** — звуковые/визуальные предпочтения с объяснением, какие сигналы поддерживаются.
4. **AI и модели** — provider, model, key management, status/connection.
5. **Хранилище и данные** — локальные предпочтения, project storage status и фактические предупреждения о persistence.
6. **Аккаунт и безопасность** — профиль, сессия, пароль, выход — только после создания/подтверждения соответствующих API.

Для каждого параметра указывать scope:
- «Сохраняется на этом устройстве» — localStorage.
- «Действует до перезапуска сервера» — in-memory AI key connection.
- «Хранится в аккаунте» — только если backend действительно это гарантирует.

Сохранить текущие функции. Не переводить локальные настройки на сервер без необходимости и отдельного решения.

### 6.3 Что отсутствует

Не обнаружены полноценные пользовательские интерфейсы/API для:
- редактирования профиля пользователя;
- смены пароля;
- восстановления пароля;
- подтверждения email;
- списка активных пользовательских сессий и отзыва сессий;
- настройки пользовательской MFA;
- управления личными API tokens.

Это будущие продуктовые функции, не существующие настройки. Не рисовать их как работающие элементы.

## 7. Пользовательская авторизация

### 7.1 Подтверждённая backend-логика

Серверные endpoints:
- `POST /api/auth/register` — email, name, password; минимальная длина пароля 8 символов; rate limiting.
- `POST /api/auth/login` — проверка пароля, создание session cookie.
- `GET /api/auth/me` — получение текущего пользователя.
- `POST /api/auth/logout` — отзыв текущей сессии и очистка cookie.
- `POST /api/auth/admin-mfa/challenge/verify` — отдельный административный MFA challenge; не является общей MFA для обычных пользователей.

Backend использует scrypt password hash, подписанную session token cookie с HttpOnly, SameSite=Lax и Secure в production, серверную таблицу auth_sessions, проверку revoked/expiry/idle timeout и rate limiting.
Production требует `NEXUM_AUTH_ENABLED=true` и `NEXUM_AUTH_SECRET` не короче 32 символов.

### 7.2 Обнаруженное несоответствие пользовательского UI

`AuthGate` содержит формы login/register и MFA challenge. Однако в `App.tsx` текущий root export оборачивает через AuthGate только ветку `/admin`. Основной WorkspaceApp возвращается напрямую.

При этом:
- API `/api/projects` защищён auth middleware;
- API `/api/chat` защищён auth middleware;
- agent history/profiles/diagnostics и business-agent endpoints также требуют auth;
- production запрещает выключать authentication.

Таким образом, статический аудит показывает риск: обычный пользователь может увидеть оболочку Workspace, но UI не предлагает ему войти/зарегистрироваться, если API отвечает 401. Это необходимо проверить в реальном production-like runtime перед редизайном и устранить отдельной задачей пользовательского auth flow.

### 7.3 UX-направление

Сделать самостоятельный пользовательский auth flow:
- login;
- registration;
- loading session;
- expired/invalid session;
- rate limit / temporary service unavailable;
- logout;
- preserve return path (вернуться в исходный project route после успешного входа).

AuthGate для admin не использовать как готовую пользовательскую форму без отдельного разделения контекстов. Административный MFA challenge не переносить в пользовательский login.

Не добавлять UI восстановления пароля, смены пароля, email verification или пользовательской MFA, пока backend endpoints и security design не готовы.

### 7.4 Безопасность

- Не хранить пароль или session token в localStorage.
- Cookie остаётся HttpOnly; клиент проверяет сессию через `/api/auth/me`.
- Все API 401 должны приводить к понятному состоянию входа, а не к пустой странице/бесконечной загрузке.
- 503 от auth/session service должен отличаться от invalid credentials.
- Не раскрывать, существует ли email в системе, сверх принятой backend policy.
- Rate-limit responses должны иметь понятный retry guidance, если Retry-After предоставлен.
- Logout должен подтверждаться ответом сервера.
- Сохранить server-side authorization как единственный источник истины.

## 8. Общая композиция и навигация

В рамках Balanced:
- Vercel clarity — простая навигация и предсказуемые состояния.
- Linear consistency — компактная типографика, понятные настройки и семантические статусы.
- Cursor transparency — техническая диагностика с реальными событиями и деталями.
- Не использовать перегруженные dashboards, декоративные графики и яркие карточки без функциональной причины.

Рекомендуемая структура:
- Интеграции — каталог реальных подключений и AI providers.
- Диагностика — техническая хронология, фильтры, детали и экспорт.
- Журнал КВАРД — редакционные заметки и подтверждённые релизы.
- Настройки — preferences, AI, workspace, storage, account.
- Аккаунт — login/register как самостоятельное состояние приложения, не смешанное с admin.

Все разделы должны иметь empty/loading/error/retry states, сохранять контекст маршрута, поддерживать desktop/tablet/mobile, light/dark и keyboard navigation.

## 9. Предлагаемые улучшения, требующие backend-аудита

1. Постоянное и безопасное хранение AI credentials (encrypted at rest, user scoped, rotation, deletion, no plaintext retrieval).
2. Реальные connector adapters: OAuth/API auth, callback, status, disconnect, token refresh.
3. Отдельная область подключения: user / project / organization.
4. Диагностика: pagination, date filters, event source, retention policy, stable IDs.
5. Unified trace model для browser diagnostics, AgentHistory и chat job events — только с корректной авторизацией и безопасной redaction.
6. Релизный pipeline для Journal: approved release metadata and commit/deploy association.
7. Account API: profile update, password change/reset, email verification, session listing/revocation — с отдельной security review.
8. Восстановление пользовательской сессии и redirect return path.
9. Унификация AI provider settings, удаление дублей только после подтверждения feature parity.
10. Экспорт диагностики с redaction preview и явным подтверждением включаемых полей.

## 10. Acceptance criteria

### Интеграции
- [ ] Ни одна карточка не показывает connected без server-confirmed status.
- [ ] AI providers отделены от external service connectors.
- [ ] Видно, является ли ключ временным или постоянным.
- [ ] Секреты не отображаются повторно и не попадают в browser storage.
- [ ] Не реализованные сервисы честно помечены как недоступные.

### Диагностика
- [ ] Источник каждого события понятен.
- [ ] Job status не смешан с runtime event level.
- [ ] Сводные числа имеют ясный sample scope.
- [ ] Ошибки, empty state и retry работают.
- [ ] Export сохраняет полезные данные и не раскрывает секреты.
- [ ] Retention/persistence limitations описаны корректно.

### Журнал
- [ ] Все записи имеют проверенные даты и тип.
- [ ] Релиз не появляется без подтверждённого deploy/release.
- [ ] Планируемые функции не выдаются за реализованные.
- [ ] Архивные редакционные заметки визуально отделены от релизов.

### Настройки
- [ ] Для каждой настройки указан scope хранения.
- [ ] Локальные preferences не выданы за account preferences.
- [ ] AI key flows проверяют статус через backend.
- [ ] Сохранены существующие работающие настройки.
- [ ] Нет кнопок профиля/пароля/сессий без реального API.

### Авторизация

## 12. UX-референсы

### OpenAI Agents Tracing
https://developers.openai.com/api/docs/guides/agents-api/tracing

Полезная структура: session → turn → span. Пользователь сначала видит общий контекст, затем отдельные вызовы модели/инструментов, длительность и outcome. Для КВАРД это ориентир детализации Agent run, а не требование копировать OpenAI backend.

### OpenAI Agents Observability
https://developers.openai.com/api/docs/guides/agents-api/observability

Полезно разделять live progress, сохранённую историю и usage. Отсутствующее usage должно оставаться unknown, а не отображаться как 0. Для КВАРД — аналогичный принцип при диагностике и статусах.

### Linear Account Preferences
https://linear.app/docs/account-preferences

Полезный паттерн группировки предпочтений: general, interface/theme, desktop behavior и workflow settings. В КВАРД применять с явным разделением локальных настроек устройства и серверных account settings.

### Linear Security & Access
https://linear.app/docs/security-and-access

Полезный паттерн для будущего Account/Security: список активных сессий, сведения о последней активности и управляемый отзыв доступа. Не внедрять визуальные элементы без backend поддержки.
