# КВАРД — UX-спецификация AI Agents и Business Agents

**Статус:** UX-направление / спецификация, не реализация  
**Дата аудита:** 25 ноября 2026  
**Проверенная база:** `main` — `59eec8e0078663c786728356a062c33fab589033`  
**Визуальное направление:** Balanced  
**Область:** только пользовательские экраны. Административная панель, её API, маршруты, права и компоненты исключены.

---

## 1. Цель этапа

Сформировать понятную и последовательную рабочую среду для двух существующих классов агентов:

1. Персональные AI-агенты, которые пользователь настраивает и передаёт в Project Studio.
2. Бизнес-агенты организации, которые публикуются, получают задания через Worker, используют знания и участвуют в командных процессах.

Это два разных продукта внутри КВАРД. Их нельзя сводить к одному списку карточек: различаются область владения, модель доступа, жизненный цикл, runtime и доступные операции.

**Основное UX-обещание:** пользователь всегда понимает, какого агента он настраивает, где он работает, что ему разрешено, что происходит при запуске и какое действие требует его решения.

## 2. Подтверждённая текущая архитектура

### 2.1 Персональные AI-агенты — `/agents`

Экран: `apps/web/src/components/AgentsPage.tsx`.

Подтверждённые возможности:

- Встроенные профили задач: разработчик, технический аудитор, инженер тестирования, DevOps-инженер.
- Создание и удаление собственных prompt-профилей.
- Отображение режима хранения профилей: PostgreSQL или память сервера.
- Создание, редактирование, удаление и пауза/активация персональных определений агента.
- Системная инструкция, описание, провайдер и модель.
- Список разрешённых инструментов (до 32, allowlist проверяется сервером).
- Политики подтверждения: `always`, `writes`, `autonomous`.
- Выбор активного проекта и передача задачи в Studio.
- Диагностика задач из `/api/agent/diagnostics`: очередь/выполнение/завершение/ошибка/отмена, события и агрегированное число ошибок.
- Отображение фактического времени обновления диагностических данных.

Важные ограничения:

- Профиль — это повторно используемая инструкция, а не отдельный постоянно опубликованный агент.
- Определение персонального агента передаётся в существующий chat/Studio runtime; запуск не является отдельным автономным расписанием.
- При отсутствии БД персональные профили и определения хранятся в памяти процесса и теряются при перезапуске.
- `autonomous` ограничен инструментами READ; это не неограниченный автономный режим.
- `always` требует подтверждения перед каждым вызовом инструмента; `writes` — перед WRITE/EXECUTE/DESTRUCTIVE; разрешение одноразовое, запрос истекает через 10 минут.
- История на странице — общая диагностика runtime, а не полноценная история запусков с отдельной карточкой каждого агента.
- Расписания и триггеры не включены.

### 2.2 Бизнес-агенты — `/business-agents`

Экран: `apps/web/src/components/BusinessAgentsPage.tsx`.

Подтверждённые возможности:

- Выбор рабочего пространства организации; создание пространства при его отсутствии.
- Каталог агентов организации с версиями, провайдером, моделью и статусами.
- Создание агента как черновика.
- Публикация и приостановка агента.
- Запуск задания для опубликованного агента.
- Очередь запусков и фоновый Worker с lease/heartbeat.
- Статусы выполнения: queued, initializing, planning, running, waiting_approval, completed, failed, cancelled, timed_out, limit_reached.
- События запуска и обновление состояния на клиенте с периодическим опросом.
- База знаний: создание текстовых источников, разбиение на фрагменты, полнотекстовый поиск и привязка источника к агенту.
- Согласования: список ожидающих решений, одобрение/отклонение.
- Квоты и использование организации.
- Команды агентов (Workforces): создание последовательности опубликованных агентов.
- API генерации черновика агента через Invent.
- Ограничения на итерации, вызовы инструментов, длительность и токены на запуск.
- Конфигурационные типы каналов, триггеров, режимов, памяти и разрешений.

Важные ограничения:

- UI создания пока показывает только название, описание, провайдера, модель, инструкции и инструменты; часть расширенной конфигурации задаётся жёстко в коде.
- API умеет обновлять конфигурацию агента и создавать новые версии, но текущий пользовательский экран не предоставляет полноценного редактирования агента.
- Каналы и триггеры могут сохраняться как конфигурация, но соответствующие адаптеры/планировщик не подключены. Нельзя изображать их как работающие интеграции или автоматизации.
- База знаний сейчас принимает текст; загрузка файлов и управление версиями источников в этом UI не реализованы.
- Вкладка команд создаёт линейный граф start → выбранные агенты → output. Backend валидирует условные узлы и умеет исполнять workforce-граф, но текущий UI не является визуальным редактором графа и не запускает сохранённые команды.
- Карточка запуска показывает только текущий/последний запуск в состоянии компонента; полноценный список истории запусков на экране не реализован.
- Согласования в списке показывают краткое описание, run ID и дату; полноценный просмотр безопасного preview аргументов в этом разделе пока отсутствует.
- Решения по согласованиям доступны ролям owner/admin; интерфейс должен учитывать фактические права пользователя.
- Вкладка использования сейчас выводит JSON квот; визуальные метрики допустимы только при привязке к реальным полям ответа API.

### 2.3 Реестр инструментов бизнес-агентов

Текущий серверный реестр `apps/api/agents/tools/toolRegistry.ts` содержит:

- `email_draft` — подготовка черновика письма, не отправляет письмо.
- `json_parse` — разбор JSON.
- `human_approval` — создание запроса на согласование, не исполняет само внешнее действие.

Инструменты имеют схемы входных/выходных данных, scopes и уровень риска. Интерфейс должен отображать фактический серверный каталог, а не статический перечень несуществующих интеграций.

### 2.4 Два контура нельзя смешивать

| Критерий | AI-агенты | Бизнес-агенты |
|---|---|---|
| Область владения | Аккаунт пользователя | Организация |
| Главная задача | Работа в контексте проекта | Бизнес-процесс организации |
| Жизненный цикл | Активен / пауза | Черновик / опубликован / пауза / архив |
| Исполнение | Через Studio / chat job | Через очередь и Worker |
| Конфигурация | Инструкция, модель, allowlist, approval policy | Версионируемая AgentConfig |
| Знания | Контекст проекта и его файлы | Организационная база знаний |
| Команды | Не предусмотрены в этом разделе | Workforces |
| Автоматические триггеры | Не включены | Типы конфигурации есть, адаптеры не подтверждены |
| История | Общая runtime-диагностика | Run/events API; полноценная история в UI отсутствует |

## 3. UX-принцип и визуальное направление

Сохраняем утверждённую комбинацию:

- **Vercel clarity:** понятная структура объектов, фильтрация и лаконичные списки.
- **Lovable interaction:** настройки агента и результат работы должны быть близко, без лишних переходов.
- **Cursor transparency:** видимые шаги, инструменты, разрешения, ошибки и возможность остановить выполнение.
- **Linear consistency:** строгая типографика, спокойные поверхности, предсказуемые состояния и единые паттерны.

Для КВАРД это означает Balanced: спокойная технологичная оболочка, чистая сетка, выразительная типографика, умеренный фирменный акцент. Не превращать страницы в набор разноцветных дашборд-карточек. Цвет статуса — только семантический. Никаких декоративных графиков и выдуманных показателей.

## 4. Информационная архитектура

### 4.1 AI-агенты

Маршрут остаётся `/agents`. Внутри экрана выделить три логических раздела:

1. **Профили** — библиотека готовых и пользовательских инструкций.
2. **Мои агенты** — постоянные персональные конфигурации и их политики.
3. **Выполнение** — фактические задания и события runtime.

Не смешивать профили с определениями агентов в одном визуальном типе. Профиль — шаблон инструкции; агент — сохранённая конфигурация с доступом к инструментам.

Предлагаемая композиция:

- Заголовок и краткое назначение раздела.
- Компактная навигация между тремя разделами.
- Внутри «Профили» — библиотека шаблонов и форма создания.
- Внутри «Мои агенты» — список конфигураций; выбранный агент раскрывает настройки и действия.
- Внутри «Выполнение» — таблица задач и лента событий, фильтры по статусу и периоду только после подключения к реальным параметрам API.
- Запуск выбранного агента ведёт в Studio с уже подставленной задачей; перед отправкой пользователь видит её в composer.

Не добавлять отдельные метрики использования, стоимость или успешность по агентам, пока API не отдаёт соответствующие агрегаты.

### 4.2 Бизнес-агенты

Маршрут остаётся `/business-agents`. Организация — постоянный контекст страницы, выбранная организация должна быть заметна в заголовке.

Существующие разделы сохранить, но привести к единой навигации:

1. **Агенты**
2. **База знаний**
3. **Команды**
4. **Согласования**
5. **Использование**

В «Агентах» сохранить двухколоночную схему: слева каталог, справа выбранный агент. На мобильном — список и детали как последовательные экраны/переключаемые состояния, без сжатия колонок.

Вкладки базы знаний, команд, согласований и использования должны сохранять контекст организации и показывать самостоятельные empty/loading/error states.

## 5. Ключевые пользовательские сценарии

### 5.1 Создать персонального AI-агента

1. Пользователь открывает «Мои агенты».
2. Создаёт агента: название, назначение, инструкция.
3. Выбирает провайдера/модель или режим по умолчанию.
4. Разрешает только нужные инструменты.
5. Выбирает политику подтверждения; интерфейс объясняет реальные последствия.
6. Сохраняет конфигурацию.
7. Выбирает активный проект, вводит задачу и открывает её в Studio.
8. В Studio проверяет текст задачи и запускает.
9. При запросе разрешения видит инструмент, риск, preview аргументов и срок действия; разрешение одноразовое.

### 5.2 Создать бизнес-агента

1. Пользователь выбирает организацию.
2. Создаёт черновик с названием, функцией, инструкциями, моделью и инструментами.
3. Проверяет конфигурацию и доступные инструменты.
4. Публикует агента.
5. Вводит задачу и запускает.
6. Видит queued → initializing/planning/running → terminal status, события и результат.
7. Приостановка запрещает новые запуски; статус существующего запуска не должен подменяться статусом агента.

### 5.3 Управлять согласованиями

- Вкладка показывает только реальные pending approvals.
- На карточке: понятное описание действия, агент, запуск, время, статус/срок, если эти поля реально доступны.
- Перед решением — безопасный preview действия, без секретов и необработанных чувствительных payload.
- Кнопки «Одобрить» и «Отклонить» доступны только при разрешённой роли.
- После решения карточка получает фактический ответ API; нельзя оптимистично удалять её до успешного ответа.

### 5.4 Управлять знаниями

- Источник имеет название, тип, дату и статус.
- Создание текстового источника — с лимитом и понятным подтверждением сохранения.
- Привязка источника выполняется к выбранному агенту.
- Ясно показывать, к какому агенту подключается материал.
- Не изображать файловый импорт, синхронизацию внешних дисков или автоматическое обновление, пока backend этого не поддерживает.

### 5.5 Команды агентов

Текущий UI может создавать простую последовательную команду. В рамках текущей спецификации не выдавать её за полноценный визуальный workflow builder.

Следующий UX-уровень возможен только после отдельной проверки и подключения:
- визуальный граф с узлами Start / Agent / Condition / Output;
- валидация связей до сохранения;
- запуск графа;
- отображение хода выполнения каждого узла;
- повторный запуск и диагностика ошибок.

До этого оставить честное описание текущей возможности: создание последовательности опубликованных агентов и сохранение команды. Не показывать активную кнопку запуска, если интерфейс не вызывает соответствующий API.

## 6. Состояния интерфейса

Каждый раздел должен иметь:

- Initial loading — скелетон/нейтральное состояние без фиктивных данных.
- Empty — объяснение, что создать первым, и один релевантный CTA.
- Error — сообщение API, повторная попытка, сохранение введённых пользователем данных.
- Saving — блокировка повторной отправки и ясный индикатор.
- Success — подтверждение только после ответа сервера.
- Permission denied — объяснение, что операция требует роли owner/admin.
- Storage warning — отдельное предупреждение о временном in-memory хранении.
- Stale data — дата последнего успешного обновления, если API её предоставляет.
- Responsive — корректная работа от 320 px до широкого desktop.

### Статусы запусков

Использовать единый словарь и не смешивать статус агента со статусом запуска:

| Код | UI |
|---|---|
| draft | Черновик |
| published | Опубликован |
| paused | Приостановлен |
| queued | В очереди |
| initializing | Подготовка |
| planning | Планирование |
| running | Выполняется |
| waiting_approval | Ожидает согласования |
| completed | Завершён |
| failed | Ошибка |
| cancelled | Отменён |
| timed_out | Тайм-аут |
| limit_reached | Достигнут лимит |

## 7. Предлагаемые улучшения UX, требующие backend/API-подтверждения

Это не считать реализованными функциями. Перед реализацией требуется отдельная проверка API, прав и тестов.

1. История запусков бизнес-агента с пагинацией и фильтрами. Сейчас экран получает последний запуск, но не полноценный список запусков агента.
2. Детальная страница запуска: timeline событий, результат, ошибка, модель, длительность и usage только при наличии соответствующих полей.
3. Отмена бизнес-запуска в интерфейсе. Backend route отмены существует в repository/runtime, но публичный route и UI нужно подтвердить отдельно.
4. Редактирование опубликованного бизнес-агента с понятной моделью версий и подтверждением публикации новой версии.
5. UI конфигурации memory, limits, permissions, modes, channels и triggers. Каналы/триггеры показывать как «не подключено» до появления реального adapter.
6. Invent — генератор черновика по описанию, только если пользовательский экран подключит существующий endpoint и отобразит предупреждения о неподключённых инструментах/триггерах.
7. Полноценный workforce editor и запуск команд с визуализацией node runs.
8. Расширенное управление знаниями: файлы, удаление, повторная индексация и статусы — только после появления соответствующих API.
9. Отображение квот как progress bars/usage cards после проверки схемы ответа; неизвестные значения не трактовать как ноль.
10. Ролевая доступность действий и пояснение причин недоступности.

## 8. Безопасность и доверие

- Всегда показывать область действия: личный аккаунт или организация.
- Не показывать API-ключи и credentials в настройках агента.
- Показывать только инструменты из серверного реестра.
- Не считать клиентский allowlist достаточным контролем: серверная проверка остаётся источником истины.
- Для автономного режима сохранять ограничение READ-only.
- Для подтверждения отображать server-derived risk, редактированный preview и одноразовый характер решения.
- Не выводить необработанные prompt/input/output из административной или внутренней телеметрии.
- Не обещать отправку email: текущий email tool создаёт только черновик.
- Не показывать channel/trigger как работающий, если нет интеграционного адаптера.
- Разделять ошибки модели, ошибки инструмента, ограничения квот и недоступность Worker.

## 9. Визуальная система и адаптивность

- Повторно использовать утверждённые токены Balanced и компоненты UI Kit; не вводить вторую палитру специально для AI.
- Списки — компактные, с ясной иерархией имени, назначения, модели и статуса.
- Детали — структурированные секции с группировкой по смыслу, не длинная форма из десятков полей.
- Опасные/необратимые операции — с явным подтверждением.
- Motion — короткий и функциональный: смена вкладок, раскрытие деталей, обновление статуса, появление approval.
- Не использовать бесконечные пульсации, фальшивую активность, искусственные графики.
- Desktop: каталог + detail pane.
- Tablet: адаптивная двухколоночная композиция или список → детали.
- Mobile: одна колонка, листинг и детали разнесены по состояниям; формы на всю доступную ширину.
- Проверить light/dark, клавиатуру, фокус, контраст, reduced motion и отсутствие горизонтального overflow на 320 px.

## 10. Acceptance criteria

### AI Agents
- [ ] Профили визуально отделены от персональных определений агентов.
- [ ] Все существующие операции сохранены: create/edit/delete/pause/activate.
- [ ] Storage mode и ошибки загрузки видимы и понятны.
- [ ] Политики подтверждения объясняются без двусмысленности.
- [ ] Передача задачи в Studio сохраняет выбранный проект, агента и текст задачи.
- [ ] Runtime status и события поступают из реального API.
- [ ] Нет fake run history, usage, schedules или integrations.

### Business Agents
- [ ] Организация явно обозначена как текущий контекст.
- [ ] Список и детали агента согласованы по состояниям.
- [ ] Черновик нельзя запустить до публикации.
- [ ] Публикация/пауза и запуск отражают ответы API.
- [ ] Run status и events отображаются раздельно от agent status.
- [ ] База знаний показывает только подтверждённые типы источников.
- [ ] Согласования учитывают owner/admin permissions.
- [ ] Команды не выдаются за полноценный редактор/автоматизацию, пока workflow UX не реализован.
- [ ] Usage не содержит фиктивных чисел и графиков.
- [ ] Никаких заявлений о работающих расписаниях, триггерах или каналах без подключённых адаптеров.

### Общие
- [ ] Нет изменений административной панели и её API.
- [ ] Нет потери текущей бизнес-логики.
- [ ] Desktop/tablet/mobile, light/dark, keyboard/focus проверены.

## 11. План реализации после утверждения UX

1. Завершить маршрутную и API-карту двух экранов, проверить реальный runtime в браузере.
2. Утвердить общий UI Kit и паттерн списка/деталей.
3. Переработать экран `/agents` без изменения контрактов API.
4. Переработать экран `/business-agents` без изменения контрактов API.
5. Отдельно оценить backend-зависимости для run history, cancellation, agent editing, Invent и workforce execution UI.
6. Реализовывать небольшими коммитами прямо в `main`; перед каждым изменением повторно проверять HEAD и SHA файлов.
7. После каждого логического этапа — typecheck, lint, tests, build, diff review.
8. Проверить, что в diff отсутствуют admin-файлы, admin API, auth/role changes и admin styles.

## 12. Исследованные UX-референсы

### OpenAI Agents — tracing dashboard
https://developers.openai.com/api/docs/guides/agents-api/tracing

Полезный паттерн: session → turn → span. Пользователь может начать с общей сессии, затем раскрыть ход работы, отдельный вызов модели или инструмент; в деталях видны статусы, длительность и результат. Для КВАРД это ориентир будущей детальной страницы запуска, не основание придумывать trace-данные, которых сейчас нет.

### OpenAI Agents — observability and usage
https://developers.openai.com/api/docs/guides/agents-api/observability

Полезный паттерн: живые события отдельно от сохранённой истории и usage. Пустое/неизвестное значение usage не должно отображаться как ноль. Для КВАРД — разделять live progress, итоговый run и фактическую телеметрию.

### OpenAI Agents SDK — tracing
https://openai.github.io/openai-agents-js/guides/tracing/

Полезный паттерн: trace/span hierarchy для model calls, tool calls, handoffs и guardrails. Для КВАРД — использовать как концептуальный reference для читаемой хронологии действий агента.

### n8n — Agents
https://docs.n8n.io/advanced-ai/

Полезный паттерн: агент задаётся моделью, инструкциями, инструментами и подключёнными workflows; важно отличать агента от workflow и показывать, какие именно инструменты доступны ему. Не переносить в КВАРД неподключённые возможности n8n.

## 13. Зафиксированные границы

- Этот документ описывает пользовательский UX и не разрешает менять административную панель.
- Не менять API, схему БД, роли и auth в рамках чисто визуального этапа.
- Не заменять текущую агентную архитектуру новым framework ради сходства с референсом.
- Не считать спецификацию доказательством runtime-поведения: браузерная проверка интерфейса на этой итерации не выполнена.
- Не начинать реализацию расширенных функций из раздела 7 без отдельного технического аудита.
