## P0 — блокирует публичный запуск

### AUDIT-001 — агентские команды могут исполняться на хосте API

**Статус исходного снимка: CONFIRMED; текущий main: RESOLVED через PR #35 (подтверждено CI).**

Доказательства:
- `apps/api/agent/agent.ts` регистрирует и `RunCommandTool`, и `RunSandboxTool`.
- В `apps/api/agent/tools/runCommand.ts` команда запускается через `spawn(..., { shell: false })`, но непосредственно в процессе/окружении API.
- Текущая валидация допускает `npm install` без обязательного `--ignore-scripts` и `npm run` для allowlist имён скриптов. Содержимое скриптов из пользовательского `package.json` контролируется пользователем проекта, а не этим allowlist.
- Маршрут `POST /api/projects/:id/run` также вызывает `RunCommandTool` для build/test/lint/typecheck.

Почему это опасно: отсутствие shell не делает запуск кода безопасным. `npm install` может исполнять lifecycle scripts зависимостей, а разрешённый `npm run build` может запускать произвольный код из проекта. В таком виде выполнение кода проекта может получить доступ к окружению API-процесса.

Что сделать:
1. Направить все пользовательские команды выполнения кода через DockerSandbox или другой отдельный sandbox с ограниченными правами.
2. Оставить на хосте только явно безопасные read-only операции, например ограниченный Git.
3. Запуск установки зависимостей выполнять только внутри sandbox, с отключёнными lifecycle scripts там, где это совместимо с продуктом.
4. Не передавать контейнеру секреты сервера и не монтировать за пределами активного проекта лишние каталоги.
5. Добавить тесты, которые доказывают, что команды проекта никогда не вызываются напрямую на хосте.
6. Проверить также HTTP-маршруты, а не только вызовы агента.

Результат после исходного снимка: PR #35 влит в main. `RunCommandTool` направлен в DockerSandbox; GitHub CI run #2267 подтвердил прохождение build и E2E.

### AUDIT-002 — внутренние диагностика и runtime-status доступны без авторизации

**Статус исходного снимка: CONFIRMED; текущий main: RESOLVED через PR #35 (подтверждено CI).**

В `apps/api/server.ts` до middleware авторизации объявлены маршруты:
- `GET /api/diagnostics/session/:sessionId`
- `GET /api/diagnostics/latest`
- `GET /api/runtime/status`
- `POST /api/diagnostics/events`

`/api/runtime/status` возвращает список задач, информацию о процессах, идентификаторы проектов и последние runtime-диагностики. Глобальная выдача диагностики может раскрывать сообщения и метаданные разных сессий. Публичная запись диагностических событий позволяет засорять телеметрию.

Что сделать:
1. Закрыть внутренние диагностические и runtime-маршруты авторизацией и административной ролью.
2. Разделить публичную отправку клиентской телеметрии и чтение внутренних диагностик.
3. Ограничить размер и формат входящих событий, добавить rate limit.
4. Проверить отсутствие пользовательских секретов, prompt-контента и приватных путей в ответах.
5. Добавить E2E/API-тесты на ответы 401/403 для неавторизованных пользователей.

Результат после исходного снимка: защита diagnostics/runtime endpoints включена через PR #35 и прошла CI вместе с основной веткой.

## P1 — высокий приоритет

### AUDIT-003 — конфигурация из .env читается слишком рано для DB и auth

**Статус: PARTIALLY RESOLVED — чтение DB URL исправлено в main; порядок загрузки auth-конфигурации остаётся открытым.**

В `apps/api/server.ts` вызывается `dotenv.config()`, но статические ES-module imports выполняются до тела модуля. При этом:
- На исходном HEAD `apps/api/db.ts` фиксировал `process.env.NEXUM_DATABASE_URL` в константу; в текущем main URL читается через `getDatabaseUrl()` при использовании.
- `apps/api/auth.ts` по-прежнему требует отдельной проверки порядка чтения `NEXUM_AUTH_SECRET` и `NEXUM_AUTH_ENABLED`; этот файл не входил в P0 PR #35.

Если значения поступают только из локального `.env`, модули могут прочитать их до вызова `dotenv.config()`. Переменные, заданные платформой до старта процесса, не страдают от этой конкретной последовательности.

Что сделать:
1. Загружать dotenv до импорта зависимых модулей, например через ранний bootstrap/ `dotenv/config`, либо читать конфигурацию через функции после инициализации.
2. Убрать чувствительные значения конфигурации из верхнеуровневых констант, если конфигурация может загружаться позже.
3. Добавить тест запуска API с переменными только в тестовом .env и тест запуска с отсутствующими переменными.
4. Проверить, что в production отсутствующая обязательная конфигурация приводит к понятной ошибке при старте.

PR #35 меняет DB URL на чтение через функцию, но в его список изменённых файлов не входит `apps/api/auth.ts`; проблему auth-конфигурации надо проверить отдельно.

### AUDIT-004 — ChatJob cache не ограничен по размеру

**Статус исходного снимка: CONFIRMED; текущий main: RESOLVED — ChatJob cache ограничен TTL и максимальным числом записей в PR #35.**

В `apps/api/chatJobCache.ts` используется глобальный `Map`; новые сохранённые задачи помещаются в него без TTL, лимита размера или eviction. При большом числе завершённых задач процесс будет удерживать объекты в памяти.

Что сделать:
1. Ввести максимальный размер и TTL с удалением старейших записей.
2. Использовать постоянное хранилище как источник истины, а cache — только как ограниченный оптимизатор.
3. Добавить нагрузочный тест с большим количеством задач и тест eviction.
4. Согласовать поведение cache с повторным чтением из PostgreSQL.

PR #35 включает ограничение in-memory ChatJob cache и cleanup вложений. Проверить тесты и убедиться, что они покрывают долгоживущий процесс.

### AUDIT-005 — ограничение runtime-диагностик

**Статус текущего main: IMPLEMENTED; регрессионный тест добавлен отдельным изменением.**

В `apps/api/runtime/runtime.ts` хранится не более 2 000 последних диагностических событий; при превышении лимита старейшие записи удаляются. Регрессионный тест проверяет точный предел и сохранение самого нового диапазона записей.

Остаётся отдельно проверять, что диагностические события не содержат секреты, полные пользовательские промпты и содержимое файлов.

### AUDIT-006 — нет rate limiting на критичных публичных маршрутах в main

**Статус исходного снимка: CONFIRMED; текущий main: PARTIALLY RESOLVED после PR #35.**

На исходном HEAD middleware не были подключены. В текущем main middleware проверены на регистрации/входе, `/api/projects`, `/api/chat` и `/api/ai/connect-key`. Нужно завершить route-by-route review и отдельно проверить лимитирование записи диагностических событий и остальных публичных операций.

Что сделать:
1. Подключить лимиты к регистрации и логину, AI-запросам, chat/agent и диагностической телеметрии.
2. Для multi-instance развёртывания использовать общее хранилище лимитов, а не только память одного процесса.
3. Проверить IP/user ключи, заголовки Retry-After и отказоустойчивое поведение при недоступности rate-limit storage.
4. Добавить тесты превышения лимита и обхода лимита через разные маршруты.

PR #35 добавил middleware для ключевых маршрутов. Остаточная задача — подтвердить полное покрытие, ключи идентификации, Retry-After и поведение при сбое хранилища лимитов.

### AUDIT-007 — шаблон Render не описывает обязательную конфигурацию production

**Статус: PARTIALLY RESOLVED — переменные объявлены в `render.yaml`; значения и запуск production не проверены.**

`render.yaml` объявляет `NEXUM_DATABASE_URL`, `NEXUM_AUTH_SECRET`, `NEXUM_AUTH_ENABLED` и `NEXUM_CORS_ORIGINS`; секретные значения заданы как `sync: false`. Фактические значения и состояние живого сервиса из репозитория проверить нельзя. В PR #53 provider по умолчанию выровнен на `anymodel`; реальная авторизация и запрос к модели не проверялись.

Dockerfile после PR #35 использует multi-stage build, собирает API/Web и запускает `node apps/api/dist/server.js` в runtime-образе. Docker build и smoke test `/api/health` уже являются шагами CI; доступность Docker daemon для sandbox остаётся отдельным открытым вопросом.

Что сделать:
1. Сверить `render.yaml` с обязательными переменными в `apps/api/.env.example`.
2. Документировать, какие значения задаются в панели как секреты и какие безопасно хранить в YAML.
3. Настроить production build API и запуск скомпилированного JS, а не зависеть от tsx в production.
4. Добавить проверку Docker build и production smoke test в CI.
5. Проверить health-check при отсутствующей базе данных, неверном AI-ключе и неправильном auth secret.

Не делайте вывод, что текущий публичный сервис сломан: фактические значения в Render не были доступны для этой проверки.

5. Убедиться, что сборка чистого checkout работает без заранее закоммиченных node_modules.

PR #35 удалил отслеживаемые `node_modules` и обновил `.gitignore`; текущий main tree проверен — путей `node_modules/` в нём нет.

Что сделать: сохранить статический аудит, но не использовать его вместо unit/integration/E2E тестов с реальными наблюдаемыми результатами.

### AUDIT-015 — ограничения и отказоустойчивость AI-провайдеров требуют сквозной проверки

Провайдеры имеют разную поддержку capabilities, лимиты, модели и поведение при rate limit. Для каждого провайдера требуется проверить ошибки авторизации, недоступность, отмену, тайм-аут, ограничение контекста, некорректный JSON/план и поведение fallback.

Отдельно проверить, что явный выбор модели пользователя не переключается на другую модель без понятного сообщения, а исчерпание лимита не создаёт бесконечный цикл повторов.
